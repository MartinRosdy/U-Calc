# Развёртывание U-Calc на Bothost

Production-профиль: собственный Dockerfile, Telegram long polling, ровно один экземпляр,
постоянный том `/app/data`. HTTP-порт не требуется.

## 1. Подготовка GitHub

1. Загрузите проект в приватный GitHub-репозиторий и создайте Git tag релиза, например
   `v0.3.0`.
2. В Bothost создайте приложение из этого репозитория.
3. Выберите сборку собственным `Dockerfile` из корня. Не задавайте `main.py` как команду:
   Docker-образ уже запускает установленную console-команду `u-calc-bot`.
4. Оставьте один экземпляр/реплику. Второй экземпляр будет остановлен файловой блокировкой,
   чтобы два процесса не выполняли Telegram polling одним токеном.

## 2. Переменные окружения

Обязательные:

- `BOT_TOKEN` - получить у BotFather; не помещать в Git и не писать в команду запуска;
- `DATABASE_PATH=/app/data/u_calc.db`.

Рекомендуемые:

- `LOG_LEVEL=INFO`;
- `APP_TIMEZONE=Asia/Tashkent`;
- `ALLOWED_USER_IDS=123456789,987654321` для закрытого запуска;
- `RATE_LIMIT_PER_MINUTE=30`;
- `MAX_MESSAGE_LENGTH=4096`;
- `HISTORY_RETENTION_DAYS=730`;
- `DRAFT_TTL_DAYS=30`.

При пустом `ALLOWED_USER_IDS` бот публичный, но ограничения частоты и размера ввода всё
равно действуют. Токен в логах не печатается.

## 3. Постоянные данные

Подключите persistent volume к `/app/data`. Без него SQLite исчезнет при пересоздании
контейнера. Entrypoint создаёт каталог, передаёт его непривилегированному пользователю
`ucalc` и до запуска проверяет запись. SQLite использует WAL и мигрирует схему при старте.

## 4. Первый запуск и проверка

После deploy откройте Logs. Нормальный запуск содержит строку `U-Calc starting long polling`
с путём БД и не содержит токен. В Telegram выполните `/new`, тестовый расчёт, `/history`,
затем начните второй расчёт и проверьте `/resume` после restart приложения.

Если лог сообщает `Другой экземпляр U-Calc уже использует эту базу`, уменьшите число
реплик до одной и остановите старый процесс.

## 5. Резервная копия и восстановление

Согласованную онлайн-копию делайте SQLite-командой `.backup`, а не копированием одного
файла во время записи:

```bash
sqlite3 /app/data/u_calc.db ".backup '/app/data/u_calc-backup.db'"
```

Скачайте backup средствами файлов/томов Bothost и храните его отдельно. Для восстановления:

1. остановите приложение;
2. сохраните текущую БД как аварийную копию;
3. поместите проверенный backup по пути `/app/data/u_calc.db`;
4. убедитесь, что файл доступен пользователю контейнера;
5. запустите приложение и проверьте `/history`.

## 6. Обновление и откат

Перед deploy создайте backup. Разворачивайте конкретный Git tag. Для отката выберите
предыдущий tag/commit в Bothost и повторно разверните его. Миграции добавляющие; старый код
может не знать новые поля, поэтому при серьёзном откате восстанавливайте и соответствующую
резервную копию БД.

## 7. Диагностика

`Database directory is not writable`:

- проверьте, что том смонтирован именно в `/app/data`;
- проверьте `DATABASE_PATH=/app/data/u_calc.db`;
- пересоздайте deploy после подключения тома; не направляйте БД в read-only каталог образа.

Бот не отвечает:

- проверьте единственную реплику и startup log;
- проверьте `BOT_TOKEN` без пробелов и актуальность токена;
- проверьте, что Telegram ID входит в `ALLOWED_USER_IDS`;
- не добавляйте HTTP-порт: long polling в нём не нуждается.

## 8. Смена BOT_TOKEN

В BotFather отзовите старый токен, сохраните новый только в переменной `BOT_TOKEN` Bothost
и выполните restart/redeploy. Не вставляйте токен в тикет, лог, `.env.example` или Git.
Если токен когда-либо попал в Git, считайте его раскрытым и немедленно отзовите.
