# Развёртывание U-Calc на Bothost

Production-профиль: собственный Dockerfile, Telegram long polling, ровно один экземпляр,
постоянный том `/app/data`. HTTP-порт не требуется.

## 1. Подготовка GitHub

1. Загрузите проект в приватный GitHub-репозиторий и создайте Git tag релиза, например
   `v1.0.0`.
2. В Bothost создайте приложение из этого репозитория.
3. Выберите сборку собственным `Dockerfile` из корня. Не задавайте `main.py` как команду:
   Docker-образ уже запускает установленную console-команду `u-calc-bot`.
4. Оставьте один экземпляр/реплику. Второй экземпляр будет остановлен файловой блокировкой,
   чтобы два процесса не выполняли Telegram polling одним токеном.

## 2. Переменные окружения

Обязательные:

- `BOT_TOKEN` - получить у BotFather; не помещать в Git и не писать в команду запуска;
- `DATABASE_PATH=/app/data/u_calc.db`.

Рекомендуемые:

- `LOG_LEVEL=INFO`;
- `APP_TIMEZONE=Asia/Tashkent`;
- `ALLOWED_USER_IDS=123456789,987654321` для закрытого запуска;
- `RATE_LIMIT_PER_MINUTE=30`;
- `GLOBAL_RATE_LIMIT_PER_MINUTE=600`;
- `CALCULATION_RATE_LIMIT_PER_MINUTE=6`;
- `MAX_MESSAGE_LENGTH=4096`;
- `HISTORY_RETENTION_DAYS=730`;
- `DRAFT_TTL_DAYS=30`.

При пустом `ALLOWED_USER_IDS` бот публичный, но персональный и общий минутные лимиты,
отдельный лимит тяжёлых расчётов и ограничение размера ввода всё равно действуют. Общий
лимит защищает процесс, даже если нагрузка приходит от множества разных аккаунтов.
Ошибочные и отклонённые персональным лимитом запросы тоже расходуют общий бюджет, а
частота ответов о перегрузке ограничена, чтобы сам защитный путь не создавал нагрузку.
Токен в логах не печатается; приложение дополнительно вырезает его
обычную и URL-кодированную формы из готовых log-сообщений и traceback сторонних библиотек.
Даже при публичном доступе расчёты работают только в личном чате: обновления из групп,
супергрупп и каналов отклоняются до обработчиков, чтобы история и PDF не публиковались
случайно. Добавлять бота в рабочие группы не требуется.

## 3. Постоянные данные

Подключите persistent volume к `/app/data`. Без него SQLite исчезнет при пересоздании
контейнера. Entrypoint создаёт каталог, передаёт его непривилегированному пользователю
`ucalc` и до запуска проверяет запись. SQLite использует WAL и мигрирует схему при старте.
Новые базы используют incremental auto-vacuum; retention выполняет ограниченную очистку
свободных хвостовых страниц, не блокируя запуск полным `VACUUM`. Для старой базы режим
не меняется автоматически, чтобы не выполнять скрытую тяжёлую перестройку файла.
Retention запускается при старте и повторяется каждые 24 часа; временная ошибка SQLite
журналируется и повторяется на следующем цикле, не останавливая Telegram polling. При
SIGTERM уже начатая очистка завершается до освобождения polling-lock и остановки процесса.
Перед `mkdir/chown` entrypoint канонизирует путь и требует, чтобы родитель файла находился
внутри `/app/data`; traversal через `..`, symlink наружу, путь к самому каталогу или иной
root отклоняются без изменения прав файловой системы. Entrypoint устанавливает `umask 077`:
новые файлы БД, WAL, lock и backup создаются с приватными правами владельца `ucalc`.
При старте repository и polling-lock дополнительно применяют mode `0600` к существующим
SQLite/WAL/SHM и lock, исправляя наследованные права предыдущих версий.
Текущая schema v8 добавляет приватный минимальный `audit_events`; миграция выполняется
идемпотентно и не переписывает существующие расчёты или PDF.
До миграций приложение выполняет SQLite `quick_check`, а после них повторяет проверку.
Повреждённая база и schema новее поддерживаемой приводят к безопасному отказу до Telegram
polling; код не пытается понизить версию или продолжить работу с сомнительным файлом.

Пользователь может удалить все свои записи рабочей базы через `/delete_my_data`. Это не
перезаписывает старые `.backup` и логи Bothost, поэтому оператор должен задать срок их
хранения, ограничить доступ и удалять просроченные резервные копии по своей политике.

## 4. Первый запуск и проверка

Перед включением постоянного процесса запустите одноразовую команду того же образа и тома:

```bash
u-calc-doctor
```

Она не подключается к Telegram, но проверяет production-конфигурацию, timezone, запись и
миграции SQLite, `integrity_check`, schema v8, polling-lock, совпадение версий приложения
и движка, версии каталога/норм, rate limits и retention. Нормальный результат содержит
`U-Calc doctor: OK`; токен никогда не печатается. Код 2 означает, что deploy запускать
нельзя до исправления показанной ошибки. Если doctor сообщает о другом экземпляре,
остановите текущий бот перед maintenance-проверкой.

После deploy откройте Logs. Нормальный запуск содержит строку `U-Calc starting long polling`
с путём БД и не содержит токен. В Telegram выполните `/new`, тестовый расчёт, `/history`,
затем начните второй расчёт и проверьте `/resume` после restart приложения.
Polling явно обрабатывает SIGTERM aiogram: при restart/deploy цикл останавливается, а
HTTP-сессия Telegram закрывается в `finally` до завершения процесса.

Если лог сообщает `Другой экземпляр U-Calc уже использует эту базу`, уменьшите число
реплик до одной и остановите старый процесс. Если lock содержит корректный идентификатор,
сообщение дополнительно показывает `PID …`; вручную удалять lock-файл не требуется —
операционная система освобождает advisory lock при завершении владельца.

## 5. Резервная копия и восстановление

Согласованную онлайн-копию делайте установленной командой U-Calc, а не копированием
одного файла во время записи. Команда использует SQLite backup API, включает committed
WAL, запускает `PRAGMA integrity_check`, выполняет `fsync` файла и каталога и не
перезаписывает существующий файл:

```bash
u-calc-backup --output /app/data/u_calc-backup-2026-10-12.db
```

Без `--output` имя с UTC-временем создаётся автоматически рядом с рабочей базой.
Успешная команда печатает абсолютный путь и версию схемы; любой отказ завершается
кодом 2 и удаляет только созданный ею неполный файл.

Скачайте backup средствами файлов/томов Bothost и храните его отдельно. Для восстановления:

1. остановите приложение;
2. загрузите выбранный backup на persistent volume, не заменяя рабочий `.db`;
3. запустите одноразовый maintenance-контейнер того же образа и volume с командой:

   ```bash
   u-calc-restore --backup /app/data/u_calc-backup-2026-10-12.db --yes
   ```

4. сохраните отдельно путь аварийной копии `*-pre-restore-*.db`, напечатанный командой;
5. запустите приложение и проверьте `/history`.

Restore проверяет целостность и версию схемы, отказывается работать при занятом
polling-lock, повторно сверяет schema фактически скопированного снимка, очищает старые
`-wal/-shm`, атомарно заменяет рабочую базу и синхронизирует directory entry. Не заменяйте
один файл `.db` вручную и не запускайте restore одновременно с ботом.

## 6. Обновление и откат

Перед deploy создайте backup. Разворачивайте конкретный Git tag. Для отката выберите
предыдущий tag/commit в Bothost и повторно разверните его. Миграции добавляющие; старый код
может не знать новые поля, поэтому при серьёзном откате восстанавливайте и соответствующую
резервную копию БД.

## 7. Диагностика

`Database directory is not writable`:

- проверьте, что том смонтирован именно в `/app/data`;
- проверьте `DATABASE_PATH=/app/data/u_calc.db`;
- пересоздайте deploy после подключения тома; не направляйте БД в read-only каталог образа;
- убедитесь, что `DATABASE_PATH` указывает на файл, а не на сам каталог `/app/data`;
- не используйте путь вне `/app/data`, `..` или symlink на внешний каталог: entrypoint
  специально отклоняет их до рекурсивного изменения владельца;
  ошибка открытия SQLite завершается до подключения к Telegram и не выводит traceback.

Бот не отвечает:

- проверьте единственную реплику и startup log;
- остановите процесс и запустите `u-calc-doctor` на том же persistent volume;
- проверьте `BOT_TOKEN` без пробелов и актуальность токена;
- разовое предупреждение о сетевой ошибке обновления меню не останавливает polling:
  aiogram продолжает подключение с backoff; повторяющаяся ошибка авторизации означает
  неверный или отозванный токен;
- API-отклонение токена завершается кодом 2 без traceback и без значения токена в логе;
  замените `BOT_TOKEN` в environment и пересоздайте deploy, не публикуя старый токен;
- проверьте, что Telegram ID входит в `ALLOWED_USER_IDS`;
- не добавляйте HTTP-порт: long polling в нём не нуждается.

`SQLite не прошла проверку целостности` или `schema v…` новее поддерживаемой:

- не удаляйте и не редактируйте рабочую БД вручную;
- остановите приложение и скачайте рабочий файл вместе с доступными backup;
- для повреждения восстановите последний проверенный backup штатной командой из раздела 5;
- для более новой схемы разверните совместимую новую версию приложения либо восстановите
  backup, созданный до обновления; старый образ не должен открывать новую БД.

## 8. Смена BOT_TOKEN

В BotFather отзовите старый токен, сохраните новый только в переменной `BOT_TOKEN` Bothost
и выполните restart/redeploy. Не вставляйте токен в тикет, лог, `.env.example` или Git.
Если токен когда-либо попал в Git, считайте его раскрытым и немедленно отзовите.
