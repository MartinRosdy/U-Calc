# U-Calc — Telegram-бот расчёта теплопотерь

U-Calc помогает мастеру отопления оценить пиковую тепловую нагрузку квартиры или
частного дома. Бот показывает не только итоговые кВт, но и исходные данные, `R`, `U`,
`ΔT`, потери каждой конструкции, воздухообмен, мостики холода и отдельный
эксплуатационный запас.

Это прозрачный предварительный инженерный расчёт, а не автоматически готовая проектная
документация. ГВС и месячное потребление энергии в результат не входят.

## Возможности

- быстрый и расширенный сценарии расчёта;
- квартира (средний, первый, последний этаж) или частный дом;
- стены общей площадью, по размерам, периметру или отдельными группами через
  пошаговый редактор; текстовый импорт оставлен как экспертный режим;
- до 10 последовательных слоёв в каждой пошагово собранной конструкции стены;
- структурированная ориентация каждой стены с нормативной добавкой β и наследованием
  привязанными окнами и дверями;
- материалы и утеплители из версионируемого каталога либо паспортная `λ`;
- группы окон и дверей с количеством, размерами, паспортным `U` и привязкой к стене;
- пошаговый редактор групп окон и дверей с немедленной проверкой площади выбранной стены;
- пол/потолок к улице, грунту, холодной зоне или отапливаемому соседу;
- до 10 последовательных слоёв пола, перекрытия или кровли в расширенном режиме;
- фактическая температура соседней зоны и реальная конструкция перекрытия;
- зональный пол по грунту по приложению 9 ШНҚ 2.04.05-22;
- расчётный климат Ташкента, Самарканда, Нукуса или профиль пользователя;
- средний, расчётный, экстремальный и сценарий климатического риска;
- нормативный параметр Б для встроенных городов из таблицы 4 ШНҚ 2.01.01-22;
  ручная температура и полный профиль другого города хранят свой источник;
- раздельные потоки вентиляции и инфильтрации, включая формулы 2–5 приложения 8
  ШНҚ 2.04.05-22: готовый `Δp` либо его экспертный расчёт по высоте, ветру и давлению,
  ввод `Ru`, `Gn`, площадей и стыков; КПД рекуперации только механического потока;
- процентная оценка мостиков холода либо пошаговый точный ввод `ψ × L`;
- приватная история каждого Telegram-пользователя с кнопочными карточками, просмотром
  отчёта, повторным скачиванием неизменяемого PDF конкретной версии, новой версией,
  сравнением и точечным либо полным удалением; карточка показывает дату и автора версии;
- главное меню и кнопочный CRUD профилей расчёта;
- автоматическое применение default-профиля к температуре, воздухообмену и запасу;
- кнопочное редактирование этих параметров профиля с версионированием;
- устойчивые черновики, повторный показ шага после `/resume`/`/back` и защита от
  параллельных действий одного пользователя;
- автоматическое закрытие использованной inline-клавиатуры, чтобы старые вопросы не
  выглядели активными;
- настройка языка RU/UZ Latin с проверкой равенства ключей локализации;
- настраиваемое имя мастера или организации в PDF-отчёте;
- необязательный allowlist Telegram ID.

## Расчётная модель

Для непрозрачной конструкции:

```text
R = Rsi + Σ(d / λ) + Rse
U = 1 / R
Q = U × A × ΔT
```

Направление теплового потока хранится явно (`стена`, `пол`, `потолок`, `кровля`).
Поверхностные сопротивления выбраны по ISO 6946:2017: `Rsi=0,13` для стены,
`0,17` для потока вниз, `0,10` для потока вверх; для наружной поверхности
`Rse=0,04 м²·К/Вт`.

Воздушные потери:

```text
Qmech = 0,33 × Lmech × ΔT × (1 − η)
Qnatural = 0,33 × Lnatural × ΔT
Qinfiltration = 0,33 × Linfiltration × ΔT
```

Здесь `L` — расход воздуха в м³/ч, `η` — КПД рекуперации. Рекуперация не
уменьшает естественную вентиляцию или инфильтрацию. Быстрый режим с общей кратностью
явно считается невосстанавливаемой оценкой.
Если температура холодного подвала/чердака неизвестна, используется явно отмеченная
оценка 70% наружной `ΔT`; для упрощённого пола по грунту — 50%. Эти коэффициенты не
выдаются за нормативные.

В рекомендуемом зональном методе пола по грунту используются полосы шириной 2 м и
`R=2,1 / 4,3 / 8,5 / 14,2 м²·К/Вт`. Угловые участки первой зоны относятся к двум
примыкающим наружным стенам и считаются дважды. Для утепляющего слоя с
`λ < 1,2 Вт/(м·К)` добавляется `d/λ`.

Расчётное ядро не зависит от aiogram и тестируется отдельно. Telegram-слой не дублирует
инженерные правила.

## Локальный запуск

Нужен Python 3.11+ и токен от [@BotFather](https://t.me/BotFather).

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
export BOT_TOKEN='ваш-токен'
u-calc-doctor
u-calc-bot
```

`u-calc-doctor` выполняет production-preflight без обращения к Telegram: проверяет все
переменные окружения, timezone, доступ к каталогу SQLite, миграции, целостность, текущую
версию схемы, совпадение версии установленного пакета и расчётного движка, каталог/нормы,
лимиты, retention и отсутствие уже работающего polling-процесса. Значение `BOT_TOKEN`
команда никогда не выводит. Успешная проверка завершается строкой `U-Calc doctor: OK`
и кодом 0.

Переменные окружения:

| Переменная | Обязательна | Значение |
|---|---:|---|
| `BOT_TOKEN` | да | токен Telegram; никогда не логируется |
| `DATABASE_PATH` | нет | SQLite, по умолчанию `data/u_calc.db` |
| `LOG_LEVEL` | нет | `DEBUG/INFO/WARNING/ERROR/CRITICAL` |
| `APP_TIMEZONE` | нет | часовой пояс истории, по умолчанию `Asia/Tashkent` |
| `ALLOWED_USER_IDS` | нет | Telegram ID через запятую; пусто — доступ всем |
| `RATE_LIMIT_PER_MINUTE` | нет | максимум действий пользователя в минуту, 30 |
| `GLOBAL_RATE_LIMIT_PER_MINUTE` | нет | общий максимум действий всех пользователей в минуту, 600 |
| `CALCULATION_RATE_LIMIT_PER_MINUTE` | нет | максимум тяжёлых расчётов/PDF в минуту, 6 |
| `MAX_MESSAGE_LENGTH` | нет | предел входного текста, максимум Telegram 4096 |
| `HISTORY_RETENTION_DAYS` | нет | хранение завершённых расчётов, 730 дней |
| `DRAFT_TTL_DAYS` | нет | хранение незавершённого черновика, 30 дней |

SQLite schema v8 хранит минимальный журнал значимых операций: создание/удаление
расчёта, первое сохранение неизменяемого PDF и изменения профилей. В журнал не попадают
тексты сообщений, исходные данные расчёта, названия объектов, содержимое отчётов или
секреты. Записи аудита удаляются тем же retention-процессом, что и история.
Новые базы создаются с `auto_vacuum=INCREMENTAL`; после retention запускается ограниченный
`incremental_vacuum`, поэтому освобождённые хвостовые страницы возвращаются volume без
тяжёлого полного `VACUUM` при старте. Старые базы сохраняют свой текущий pragma-режим.
Очистка выполняется при старте и затем каждые 24 часа, поэтому сроки истории, аудита и
черновиков соблюдаются даже у polling-процесса, работающего без перезапуска месяцами.
При shutdown спящая задача отменяется сразу, а уже начатая SQLite-очистка завершается до
освобождения polling-lock — база не остаётся с работающим фоновым потоком.
Перед миграциями существующая база проходит `PRAGMA quick_check`, после миграций проверка
повторяется. Повреждённая БД и схема новее поддерживаемой останавливают запуск до polling,
не понижают `user_version` и требуют восстановления из проверенного backup.

Кнопка «Данные и приватность» и команда `/delete_my_data` после явного подтверждения
атомарно удаляют из рабочей SQLite все данные пользователя: расчёты и PDF, черновик,
профили, настройки и audit events. Операция не изменяет уже созданные резервные копии и
логи платформы — срок их хранения задаётся владельцем Bothost-проекта отдельно.

Расчёты доступны только в личном чате с ботом. Сообщения и callback-кнопки из групп,
супергрупп и каналов отклоняются до обработчиков, а системное меню команд Telegram
регистрируется только для личных чатов. Это исключает случайную публикацию объекта,
истории или PDF в общем чате. Публичный режим дополнительно ограничен одновременно
персональным и общим скользящими минутными лимитами: множество новых аккаунтов не может
обойти ограничение и создать неограниченную нагрузку на один процесс. Все попытки,
включая ошибочные и отклонённые персональным лимитом, входят в общий бюджет; при
перегрузке повторные служебные ответы и записи журнала также ограничиваются. Контур
лимитов выполняется раньше проверки private-chat и allowlist, поэтому запрещённый
групповой или неавторизованный трафик не обходит защиту процесса.

Проверки:

```bash
ruff check src tests scripts main.py
pytest -q
coverage run -m pytest -q
coverage report
python -m compileall -q src tests scripts main.py
python scripts/sync_requirements.py --check
python scripts/sync_requirements.py --check-installed
u-calc-doctor
```

Coverage измеряет только production-пакет `u_calc`; тестовые файлы не повышают показатель.
Минимальный порог 90% задан единым контрактом в `pyproject.toml` и применяется локально и в CI.

Перед production-релизом зафиксированный runtime-граф можно независимо проверить:

```bash
python -m pip install 'pip-audit==2.10.1'
pip-audit -r requirements-lock.txt --progress-spinner off
```

Проверку запускают под Python 3.11/3.12; аудитор не является зависимостью работающего
бота. Последний аудит 13.10.2026 завершился сообщением `No known vulnerabilities found`.

`requirements.txt` генерируется из runtime-зависимостей `pyproject.toml` командой без
`--check`. Немутирующий режим `--check`, используемый CI, сверяет его побайтно и требует,
чтобы каждая прямая production-зависимость имела тот же точный pin в полностью разрешённом
`requirements-lock.txt`. Режим `--check-installed` рекурсивно строит активный runtime-граф,
учитывает Python/platform markers, сверяет каждый установленный пакет и его version
specifier с lock и отклоняет пропущенные или лишние зависимости. CI выполняет эту проверку
отдельно на Python 3.11 и 3.12. Docker устанавливает runtime через constraints-файл.

`python -m build` создаёт два проверяемых релизных артефакта. Wheel содержит только
устанавливаемый пакет, шрифт и console-команды. Source distribution дополнительно содержит
Docker/compose, lock-файлы, документацию, CI, maintenance scripts и тесты, поэтому релиз
можно независимо собрать и проверить без исходного Git checkout. Состав обоих архивов
закреплён автоматическим тестом; базы, `.env`, логи и Python-кэши туда не допускаются.

## Docker и Bothost

Образ запускается без открытого порта: Telegram-бот использует long polling. Процесс
работает от непривилегированного пользователя, а entrypoint подготавливает права
смонтированного каталога данных. Multi-architecture база `python:3.12-slim` закреплена
OCI digest, поэтому плавающий тег не меняет ОС-слои уже зафиксированного релиза; digest
обновляется отдельно и осознанно вместе с повторным аудитом и Docker smoke tests.
Снижение прав выполняет уже входящий в закреплённую базу `setpriv --no-new-privs`:
дополнительный системный пакет из изменяемого APT-репозитория при сборке не загружается.
Dockerfile использует отдельный builder-stage; финальный runtime не содержит исходный
checkout, `pyproject.toml`, requirements-файлы или `setuptools`, а получает только
установленное приложение и зафиксированный граф production-зависимостей.

```bash
export BOT_TOKEN='ваш-токен'
docker compose up --build -d
docker compose logs -f bot
```

Для Bothost выберите сборку из собственного `Dockerfile`, задайте переменные окружения
из таблицы и подключите постоянное хранилище к `/app/data`. Порт публиковать не требуется.
Контейнер принимает `DATABASE_PATH` только для файла внутри канонического `/app/data`:
entrypoint разрешает вложенные каталоги, но отклоняет `/app/data` как файл, `..`, symlink
наружу и любой иной путь до выполнения root-операций с правами volume. Процесс наследует
`umask 077`, поэтому новые SQLite/WAL/lock/backup доступны только владельцу `ucalc`.
Repository и polling-lock также принудительно устанавливают mode `0600`, поэтому права
старой базы автоматически ужесточаются при обновлении и вне Docker.
`main.py` является только запасным входом после установки src-layout пакета и не
предназначен для запуска из необработанного checkout без установки зависимостей.
Полная инструкция: [`docs/BOTHOST_DEPLOY.md`](docs/BOTHOST_DEPLOY.md).

База использует WAL и `busy_timeout`; каталог `/app/data` должен быть постоянным.
Перед обновлением создайте согласованную копию штатной командой U-Calc. Она использует
SQLite online-backup API, включает committed WAL, выполняет `integrity_check` и перед
успешным завершением синхронизирует файл и запись каталога через `fsync`:

```bash
u-calc-backup --database /path/to/u_calc.db --output /path/to/u_calc-backup.db
```

Восстановление выполняется только при остановленном экземпляре бота штатной командой:

```bash
u-calc-restore --backup /path/to/u_calc-backup.db \
  --database /path/to/u_calc.db --yes
```

Команда использует тот же polling-lock, отклоняет более новую неподдерживаемую схему,
сохраняет текущую БД как `*-pre-restore-*.db`, удаляет относящиеся к прежней базе
`-wal/-shm` и атомарно устанавливает проверенную копию. Не заменяйте один `.db` вручную.

## Источники и ограничения

- пол по грунту: приложение 9
  [ШНҚ 2.04.05-22](https://lex.uz/uz/docs/-7262276?ONDATE=11.09.2024&action=compare);
- климат: [ШНҚ 2.01.01-22](https://lex.uz/uz/acts/-6363141);
- сопротивления поверхностей: ISO 6946:2017;
- `λ` материалов — трассируемые расчётные значения λБ из ШНҚ; `U` типовых окон/дверей остаётся справочным.

Для рабочего проекта инженер должен проверить адресный климат, влажностные условия,
паспортные `λ/U`, инфильтрацию, ориентацию и ветер, узлы мостиков холода и местные нормы.
«Климатический риск» — консервативный резерв, а не прогноз погоды на конкретную дату.

Подробная продуктовая спецификация находится в
[`docs/PRODUCT_SPEC.md`](docs/PRODUCT_SPEC.md), а принятые эксплуатационные решения —
в [`docs/ADR_PRODUCT_FOUNDATIONS.md`](docs/ADR_PRODUCT_FOUNDATIONS.md).
